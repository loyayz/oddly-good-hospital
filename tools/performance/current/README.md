# 160 人模拟步测量

`campaign160.py` 串行运行三个独立进程，每次使用相同输入，默认执行 1000 个真实前缀步和 2000 个采样步。`--prefix-steps`、`--sample-steps` 可明确指定窗口，正式采样至少 1000 步；同轮及优化对比保持窗口一致。输入保留正常入院、离院、临床、导诊、生活需求和维修，不维持固定人数。输出目录必须不存在；失败结果保留，不自动重跑。

```powershell
python -B tools/performance/current/campaign160.py --engine <Godot控制台程序> --input <160人输入> --output <新目录>
```

默认调用与 Windows 应用入口相同的 `PlatformThreadPolicy.apply_main_thread`，记录原生返回的成功状态、原因和掩码。`--main-thread-policy default` 保留平台默认调度。`OMP_NUM_THREADS=1` 不关闭 Godot 的 WorkerThreadPool。`--worker-tasks 0/1/4` 分别选择原串行环境采样、同一任务内联和四任务采样，所有业务请求保持不变。

`--profile-stages` 使用既有 `step_profile.gd` 的根阶段计时，不替换业务服务对象。阶段区间互不重叠，包含标记之间的未单独命名工作，不是函数自身 CPU 时间。报告保留计时处理、剩余时间和完整性检查；完整步的经过时间包含线程等待。诊断结果必须通过 `--exact-reference <plain目录>` 检查完整终态及有序事件的编码哈希；诊断已经完成时，也可在同一冻结源码的 plain 运行中以诊断目录为 reference，核验相同的完整编码。诊断与 plain 的时间分别记录，不把不同进程的分段时间拼成加速收益。

`--smoke` 只运行两个真实步，用于工具校验，不提供性能结论。2026-11-10 的工具校验在 `e7146a3` 游戏源码、相同 160 人输入上完成 plain 与根阶段两步运行，终态编码一致；Windows 选核返回 `applied=true`、`performance_cores`、`fc03`。首次工具准备缺少原生扩展注册清单，未进入有效测量；失败日志保留在独立过程目录。

综合场景使用 `scenario=comprehensive160-v1` 的输入封套。`--require-coverage` 要求采样窗口的业务观察器通过；未实际执行的功能不计入覆盖，覆盖不足的运行不得记为有效基准。操作通过正式命令队列进入真实模拟步，命令执行成本包含在计时内；观察器在计时区间外记录事实和工作进度。160 人指初始 120 名患者、32 名员工和 8 名真实陪护；自然到院、离院和维修上门人员按原规则变化，并分别报告。

`comprehensive_prepare.gd` 从完整四层参考医院生成输入，保留原有64间房、1200件装饰、24张护理床及全部核心人物身份。A/B/C诊断历史按当前内容、诊断能力和设备等级计算，病例分别从初诊、待检查、已诊断待治疗或手术的合法边界开始；历史证据和费用不计为本轮成果。准备器仅替换旧参考输入中已核实无归属的访客占位，使用生产陪护请求和真实模拟步生成8名陪护。研究员、初阶受训医生、合法容量内的库存和磨损设备都是声明的初始经营事实，整个优化对比期间固定，不作为加速手段。

首个真实步之前，152名原始员工和患者在原楼层声明完整身体可用的公共走廊初始位置，排除房间、入口、出口和公共等待安全谓词禁止的位置；记录全部位置映射并校验只改变初始位置及修订号。陪护仍从真实入口入院。20名原常规方案的新诊病例使用实际B类病例，保留完整S13身体及原有手术请求；其后续检查与M37治疗由真实流程产生。四名清洁工初始首班休息，首个采样步的正式改班命令恢复工作，使原16处污物的清扫进入采样窗口；不改变污物工时、工具、取用、移动和安全交接规则。

```powershell
& <Godot控制台程序> --headless --path . --script res://tools/performance/current/comprehensive_prepare.gd -- --output-dir=res://.cache/<新输入目录>
```

正式三次测量前，独立运行整段业务资格检查并确定固定采样窗口。观察器要求实际初诊、检查、普通治疗、手术、护理、病房恢复、导诊、楼层交通、员工生活、研究、培训、清洁、装修、维修和升级工作，以及真实班表命令、采购凭据和临床耗材领用；每项输出实际进度、下界及是否覆盖。工作增量仅证明发生了工作，不能替代完成、治愈或结算结果。前缀、历史输入、命令接受、设施存在均不替代实际工作。未覆盖UI、渲染、存档和完整日/季度周期。

函数诊断由 `function_probe.py --output <新的冻结工程目录>` 生成。它复制明确的源码清单与运行依赖，只包装选定方法的入口/出口，验证去除包装后业务方法与原源码完全一致；`function-probe-identity.json` 保存原始及诊断身份。再运行冻结工程内的 `campaign160.py`，使用同一输入、窗口和 `--exact-reference`。`.calls.json` 记录调用数、嵌套耗时和自身耗时；嵌套耗时不能相加，带探针的完整步时间也不能作为优化收益。

模拟步验收采用 `docs/data/balance.json` 的 P95 ≤ 10 ms、P99 ≤ 15 ms、普通步最大值 ≤ 30 ms、模拟速度比 ≥ 0.99。各次运行独立判定，不使用三次平均值掩盖超标；完整步耗时与观察、初始化及诊断开销分别记录。
