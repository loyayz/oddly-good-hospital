# 160 人模拟步测量

`campaign160.py` 在独立工程中串行运行三次，每次使用相同输入、1000 个真实前缀步和 2000 个采样步。输入保留正常入院、离院、临床、导诊、生活需求和维修，不维持固定人数。输出目录必须不存在；失败结果保留，不自动重跑。

```powershell
python -B tools/performance/current/campaign160.py --engine <Godot控制台程序> --input <160人输入> --output <新目录>
```

默认调用与 Windows 应用入口相同的 `PlatformThreadPolicy.apply_main_thread`，记录原生返回的成功状态、原因和掩码。`--main-thread-policy default` 保留平台默认调度。`OMP_NUM_THREADS=1` 不关闭 Godot 的 WorkerThreadPool。`--worker-tasks 0/1/4` 分别选择原串行环境采样、同一任务内联和四任务采样，所有业务请求保持不变。

`--profile-stages` 使用既有 `step_profile.gd` 的根阶段计时，不替换业务服务对象。阶段区间互不重叠，包含标记之间的未单独命名工作，不是函数自身 CPU 时间。报告保留计时处理、剩余时间和完整性检查；完整步的经过时间包含线程等待。诊断结果必须通过 `--exact-reference <plain目录>` 检查完整终态及有序事件的编码哈希。诊断与 plain 的时间分别记录，不把不同进程的分段时间拼成加速收益。

`--smoke` 只运行两个真实步，用于工具校验，不提供性能结论。2026-11-10 的工具校验在 `e7146a3` 游戏源码、相同 160 人输入上完成 plain 与根阶段两步运行，终态编码一致；Windows 选核返回 `applied=true`、`performance_cores`、`fc03`。首次工具准备缺少原生扩展注册清单，未进入有效测量；失败日志保留在独立过程目录。

测量记录源码和输入哈希、引擎及 DLL 身份、实际命令、选核结果、逐步时间、部门任务计数、完整世界校验和业务计数。独立进程不清空操作系统文件缓存；桌面应用继续运行，控制器每两秒检查错误日志。正式基准不与其他引擎或编译器并行。模拟步、初始化、实际呈现帧、选核控制和并行控制分别形成结论；无窗口结果不证明画面帧率或发行验收。
