# 160 人模拟步测量

`campaign160.py` 串行运行三个独立进程，每次使用相同输入，默认执行 1000 个真实前缀步和 2000 个采样步。`--prefix-steps`、`--sample-steps` 可明确指定窗口，正式采样至少 1000 步；同轮及优化对比保持窗口一致。输入保留正常入院、离院、临床、导诊、生活需求和维修，不维持固定人数。输出目录必须不存在；失败结果保留，不自动重跑。

```powershell
python -B tools/performance/current/campaign160.py --engine <Godot控制台程序> --input <160人输入> --output <新目录>
```

默认调用与 Windows 应用入口相同的 `PlatformThreadPolicy.apply_main_thread`，记录原生返回的成功状态、原因和掩码。`--main-thread-policy default` 保留平台默认调度。`OMP_NUM_THREADS=1` 不关闭 Godot 的 WorkerThreadPool。`--worker-tasks 0/1/4` 分别选择原串行环境采样、同一任务内联和四任务采样，所有业务请求保持不变。

`--profile-stages` 使用既有 `step_profile.gd` 的根阶段计时，不替换业务服务对象。阶段区间互不重叠，包含标记之间的未单独命名工作，不是函数自身 CPU 时间。报告保留计时处理、剩余时间和完整性检查；完整步的经过时间包含线程等待。诊断结果必须通过 `--exact-reference <plain目录>` 检查完整终态及有序事件的编码哈希；诊断已经完成时，也可在同一冻结源码的 plain 运行中以诊断目录为 reference，核验相同的完整编码。诊断与 plain 的时间分别记录，不把不同进程的分段时间拼成加速收益。

`--smoke` 只运行两个真实步，用于工具校验，不提供性能结论。2026-11-10 的工具校验在 `e7146a3` 游戏源码、相同 160 人输入上完成 plain 与根阶段两步运行，终态编码一致；Windows 选核返回 `applied=true`、`performance_cores`、`fc03`。首次工具准备缺少原生扩展注册清单，未进入有效测量；失败日志保留在独立过程目录。

综合场景使用 `scenario=comprehensive160-v1` 的输入封套。`--require-coverage` 要求采样窗口的业务观察器通过；未实际执行的功能不计入覆盖，覆盖不足的运行不得记为有效基准。操作通过正式命令队列进入真实模拟步，命令执行成本包含在计时内；观察器在计时区间外记录事实和工作进度。160 人指初始 120 名患者、32 名员工和 8 名真实陪护；自然到院、离院和维修上门人员按原规则变化，并分别报告。

`comprehensive_prepare.gd` 从完整四层参考医院分阶段生成输入，保留64间房、1360件设施（含1200件装饰）、24张护理床及全部核心人物身份。先将尚未参与模拟的120份原始患者/病例/到院凭据深复制为只读输入，员工世界中不保留它们的票、收费或引用；32名员工独立完成真实开院准备。正常接诊通过正式命令关闭，八台导诊护士均实际完成六秒护士工作台交接并真实走到各自岗位后，才加入120名原始患者。A/B/C诊断历史按当前内容、诊断能力和设备等级计算，历史证据及费用在患者加入边界声明，不计为本轮成果。准备器仅替换已核实无归属的访客占位，之后使用生产陪护请求和真实模拟步生成8名陪护，并重新开放正常接诊。研究员、初阶受训医生、合法容量内的库存和磨损设备都是声明的初始经营事实，整个优化对比期间固定，不作为加速手段。

初始位置分两次声明：员工在其首个真实步之前，患者在加入后、其首个真实步之前，各自在原楼层取得完整身体可用的公共走廊位置，排除房间、入口、出口和公共等待安全谓词禁止的位置。每次分别记录位置映射并校验只改变本批人物的初始位置及修订号；已走动员工的身体、位置、移动、岗位、生活需求和工时不被患者加入或部署改写。患者的到院、有效等待和生活时钟从实际加入 tick 建立，票由原排队入口按稳定身份顺序生成。已到岗护士的最终位置按真实岗位及世界规则校验，不再要求它是公共等待停点。20名原常规方案的新诊病例仍使用实际B类病例，保留完整S13身体及原有手术请求；其后续检查与M37治疗由真实流程产生。四名清洁工初始首班休息，首个采样步的正式改班命令恢复工作，使原16处污物的清扫进入采样窗口；不改变污物工时、工具、取用、移动和安全交接规则。

初始部署按实际业务入口确定距离偏好：同层房间排班员工靠近该房间门外；跨层病房护士留在原楼层的现有连接器附近，随后真实乘梯和交接；无房间排班的护士靠近本层公共护士工作台。其余无房间承诺员工保留原位置偏好。患者加入时八台护士已经实际在岗，每层30名患者仍按身份顺序交替靠近本层两台真实导诊台，各15人，不指定导诊台归属、队号或到场，也不修改后续随机选台与原行程承诺。每个偏好均枚举完整96×96楼层整数格，逐人复核完整身体、房间、门、实际岗位、预约及其他身体，不截断候选。排序只在准备器中局部复用，记录每人的入口来源、原新位置和距离。同步开院且护士尚在到岗时形成的集中拥堵输入作为独立压力场景保留；分段开院输入形成新哈希，场景修订不计为运行时代码优化收益。

患者初始分布保留坐标均为偶数格点的实验偏好，再按入口距离、纵坐标和横坐标检查其余整数格。全部9216个候选仍保留；不设置游戏最小间距，不减少人数、身体、病例或工作量，不以该偏好声明性能收益。准备报告单独列出32人阶段的真实步数、耗时、每名员工移动和实际护士交接工时、生活时钟及八台到岗时刻，再记录120人加入时刻与最终全部身份/身体。32人阶段不计为160人业务覆盖或性能。完整160人冻结后，本轮综合资格及基准固定执行1000个真实前缀步和6000个采样步，保留0.1秒步长、原规则及七个采样经营命令；覆盖仍须由实际采样验证。

B/C检查病例优先保留原物种；需要替换病例物种时，完整枚举当前内容绑定并要求包含症状包络的宽、深、高与原身体完全相同。原绑定无对应C类病例不能回退到更小的人体；加入时与最终输入均独立核对全部152名核心人物的完整身体。

正式三次测量前，独立运行整段业务资格检查并确定固定采样窗口。观察器要求实际初诊、检查、普通治疗、手术、护理、病房恢复、导诊、楼层交通、员工生活、研究、培训、清洁、装修、维修和升级工作，以及真实班表命令、采购凭据和临床耗材领用；每项输出实际进度、下界及是否覆盖。工作增量仅证明发生了工作，不能替代完成、治愈或结算结果。前缀、历史输入、命令接受、设施存在均不替代实际工作。未覆盖UI、渲染、存档和完整日/季度周期。

函数诊断由 `function_probe.py --output <新的冻结工程目录>` 生成。它复制明确的源码清单与运行依赖，只包装选定方法的入口/出口，验证去除包装后业务方法与原源码完全一致；`function-probe-identity.json` 保存原始及诊断身份。再运行冻结工程内的 `campaign160.py`，使用同一输入、窗口和 `--exact-reference`。`.calls.json` 记录调用数、包含子调用的经过时间，以及扣除其他已插桩子方法后的经过时间；后者仍含未插桩调用和等待，不是纯函数自身CPU时间。嵌套耗时不能相加，带探针的完整步时间也不能作为优化收益。

模拟步验收采用 `docs/data/balance.json` 的 P95 ≤ 10 ms、P99 ≤ 15 ms、普通步最大值 ≤ 30 ms、模拟速度比 ≥ 0.99。各次运行独立判定，不使用三次平均值掩盖超标；完整步耗时与观察、初始化及诊断开销分别记录。
