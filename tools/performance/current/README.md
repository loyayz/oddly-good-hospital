# 160 人模拟步测量

当前场景为 `comprehensive160-clinical-family-v3`，适用 [临床流程与住院家属统一规格](../../../docs/specs/26-11/2026-11-11-clinical-flow-and-inpatient-family.md)。旧 `comprehensive160-v1` 的普通门诊陪诊、证据分数和双检查输入已经退役；v2 的家属优先准备未通过资格检查。旧输入均不能作为 v3 的有效基准，历史报告、原始输出和输入哈希保留其历史意义。

[混合临床与运营行](mixed160.md)使用独立入口和显式 `--scenario mixed160-clinical-ops-v1`。它保留完整 160 核心和全部设施，将原行 84 份当前 GP 输入改为 10 份待检查、6 份待复核、68 份待常规治疗。原 v3 完整输入及其 84 份 GP 请求继续保留。不同负载两行各建基线，只在本行相同输入下比较实现；行间差异不作为优化收益。覆盖、采样、密集窗口和 CPU 门槛相同。

`campaign160.py` 默认串行启动三个独立进程，每次执行相同完整输入、1000 个真实前缀步和 6000 个采样步。每步为生产模拟的 0.1 秒。正式采样至少 1000 步；同轮与优化对比固定输入、窗口、引擎、原生库、线程策略、观察器及全部合法负载。输出目录必须不存在，失败证据保留，不自动重跑。

```powershell
python -X utf8 -B tools/performance/current/campaign160.py --engine <Godot控制台程序> --input <新160人输入> --output <新目录> --scenario comprehensive160-clinical-family-v3 --require-coverage
```

`--repeat-number 1/2/3` 每次仅执行一个完整轮次，便于串行控制和在当前轮次结束后停止。每轮独立判定 P95 ≤ 10 ms、P99 ≤ 15 ms、普通步最大值 ≤ 30 ms、模拟速度比 ≥ 0.99，不能用三轮平均掩盖超标。`--smoke` 只执行两个真实步，校验工具入口，不提供功能覆盖或性能结论。

## 输入与业务边界

`comprehensive_prepare.gd` 保留四层、64 间房、全部原 1360 件设施、1200 件装饰、24 张护理床及全部原始完整身体。另在原 GP 房内通过正式建造预览和命令增加一件 M17，总数为 1361 件设施、161 件服务对象；不移除原器材。原 GP 医生在首个员工步之前声明治疗 3 级，保持原班表和诊断能力，以满足 C 舒缓原有资格。32 名原员工先完成真实开院：八台导诊同时可用，原病房护士 25、27 按原班表实际到各自病房工作台，完成不少于 60 tick 的真实基础交接，当前无移动、生活任务和其他占用，保留原资格并可开始工作。门槛不填写准备结果或调整人员时钟。

开院完成后一次加入全部原 120 份患者和固定 8 份完整新病例，形成 `32 员工 + 128 患者 = 160` 的初始核心。患者加入后不推进任何准备步，不预刷住院、家属、手术和护理，也不按家属人数替换患者。初始家属数为零，不构成家属功能通过；两类家属必须在采样窗口真实到院、进出病房并取得有效工作证据。后续所有合法家属请求、自然到院、离院及维修上门人员继续运行，实际人数允许超过 160，每类人数、病程与密度分别报告。不能撤掉演员、取消合格请求、重抽随机结果或替换已参与患者。最终输入及其构成、随机流和哈希在优化对比期间固定。

历史临床输入由 `comprehensive_clinical_inputs.gd` 明确声明：12 份已确诊待手术入住、4 份常规待治疗、4 份 C 档舒缓待治疗、2 份信息不足待一次检查、2 份已完成一次检查待返回原 GP 免费复核，以及 20 份全新 B 档 GP 病例，其余为全新 GP 病例。保存的 GP/检查结果和已完成诊费只作为未测前提；新 GP 输入不含结果，不提前抽判断，不保存旧证据分数。每份首次加入的 Visit 都调用原研究所有者 `record_arrival`；B 档首次到院时刻据此持久记录，不依赖后续扫描补发开放事实。两份待复核病例的原门诊位于另一楼层，实际返回和复核仍须执行。C 舒缓仅保留原研究、能力、报价、耗材与真实治疗，没有强制床位和恢复。所有原床、术前等待与真实手术承诺由生产所有者建立，准备器不刷未来恢复或护理。

每个员工或患者只在自己的首个真实步之前声明一次合法初始公共位置。全部 96×96 整数格都是候选，逐人检查完整身体、房间、门、现有岗位、预约和其他身体；患者只使用原有偶数格偏好及入口距离排序。患者声明不能改写已经参与开院的员工位置、移动、工时、生活任务或占用。位置映射、加入 tick、实际开院资格、准备耗时及所有校验写入输入 manifest；后续真实住院与家属进展写入采样报告。研究、课程、合法库存、磨损设备、污物及原七类经营命令继续存在，不削减候选或工作量。

```powershell
& <Godot控制台程序> --headless --path . --script res://tools/performance/current/comprehensive_prepare.gd -- --output-dir=res://.cache/<新输入目录>
```

准备与正式计时分离。功能实现及评审修复完成后，先运行新场景资格检查，确认真实临床和经营覆盖，再冻结同一输入执行三次正式测量。资格不足的运行保留为失败，不记为有效基准。

准备失败时保存完整世界、有序事件与相关患者状态至 `comprehensive160.input.bin.failed-boundary.{bin,json}`。已有输入、manifest 或失败边界的目录均拒绝覆盖。`clinical_boundary_probe.gd --input=<边界.bin> --output=<新报告.json>` 只读检查病床兼容、身体布局、护理班表及真实路径，并验证查询前后完整世界不变；不推进模拟、抽取随机数或创建预约，其耗时不作为性能证据。

## 测量、覆盖与诊断

`--require-coverage` 要求采样窗口实际发生初诊、一次检查、复核、普通治疗、手术、苏醒、护理和返原病房，以及导诊、交通、员工生活、研究、培训、清洁、装修、维修、升级、排班、采购、耗材和真实移动。临床服务还要求对应完成事件；经营工作进度不能冒充整单完成。

家属门槛为陪同完整入房、探视家属至少一个实际有效 tick。完整出房、陪同生活和手术室外等待另列观察计数；这些门槛不证明单个访客已完成300有效tick，也不证明完整陪同生活闭环。复核门槛证明实际 consult 工作和完成，原医生身份与免费账目由临床专项验证。患者实际离院结果另列；前缀已结算、采样才离院的结果不能归为本窗口新治疗成功。初始历史、前缀、命令接受和对象存在均不替代采样工作。

有效探视只计合法房内区间的实际每步递减。患者终结时取消请求并直接清零余量不算工作，不能据此补足300 tick。`observer_contract_test.gd` 的50项计算边界检查验证计数、终结取消、医疗让位与前缀/采样分离，不推进生产业务，也不提供家属功能覆盖结论。

观察器还检查最多两次实际 Attempt、一次检查完成、冻结疗程不变、手术前真实住院、夜间不开新术、普通治疗无强制恢复、原床交接、原床的 Stay 所有权、固定陪同资格/身份、日探视结果、房外不扣探视时间、医疗前完整出房及生活后先回病房。功能专项测试和这些采样不变量分别提供证据，场景覆盖不等于全部验收用例通过。

完整模拟步经过时间包含真实派工、命令、移动与内部线程等待。命令从正式队列进入被测步，命令成本在计时内；观察与日志在步计时外，单独记录总观察开销。模拟速度比继续采用包含观察与日志的现实窗口，标明此保守范围。采用最近秩 `ceil(p × n)` 的 P95/P99 和同批最大值。实际人数达到初始 90% 的连续密集区间各自报告相同指标，至少一段达到 1000 样本；不能靠自然离院后的轻尾部稀释密集阶段。

默认使用应用入口的 `PlatformThreadPolicy.apply_main_thread`，记录原生成功状态、原因及掩码。`--main-thread-policy default` 保留系统默认调度。`OMP_NUM_THREADS=1` 不关闭 Godot WorkerThreadPool；`--worker-tasks 0/1/4` 分别使用原串行、同任务内联和四任务环境采样，业务请求不变。正式基准不与其他引擎或编译器并行，独立进程保留操作系统文件缓存及桌面应用负载。

`--profile-stages` 使用生产根阶段时间标记，不替换服务对象。阶段之间不重叠，但包含标记间未单列的工作，属于经过时间而非函数自身 CPU。`function_probe.py --output <新冻结工程目录>` 包装明确的方法入口/出口并验证还原后函数体与源文件逐字相同。`.calls.json` 的独占经过时间仅扣除其他已插桩子调用，仍含未插桩工作和等待；不能把嵌套耗时相加，也不能用带探针的整步时间声明加速。

`prepare_hotpath_diagnostic.py prepare --base-project <完整plain冻结工程> --output <新.cache工程> --input <同一输入> --reference <完整plain轮次目录>` 从该工程的来源清单复制原始文件，默认包装32个移动、空间、导航和体验采样方法，并单列环境批次的历史覆盖映射复制、线程派发、等待和结果回收。所有原文件和方法体按记录逆剥后恢复完整字节；不从当前工作区带入新业务实现。`--check-only` 只检查输入、签名和逆变换，`--methods <JSON>` 可调整方法集合，但须保留移动与体验采样的最外层入口。

计时只在采样的真实`sim.step`期间启用。主线程按最外层被探方法及父子调用边记录`.hotpath.json`，Worker调用不写共享计时状态，也不开启生产`worker_diagnostics`。导航在移动子树中的耗时与其他调用分列；最外层标签只代表被探入口，不推断未采集的调用者。`.query-counts.json`保存初始化后、采样前及窗口末的原计数和区间差值，`native_field_threads`峰值只保留原值，不计为事件次数。沿用原1000＋6000完整窗口，可先运行原两步smoke；分别执行`verify --project <工程> --diagnostic-output <轮次目录> --reference <对应plain目录>`，smoke验证另加`--smoke`。验证包括主线程栈、被探区间分区、计数差值、完整世界及有序事件、原始字节还原和源/引擎/DLL身份；业务覆盖仍单独判定，带探针的时间不能用于性能达标或收益结论。

[两步工具资格记录](../../../docs/reports/evidence/2026-11-12-clinical-performance/hotpath-overlay-smoke.json)保存0＋2步的18项独立校验、来源与运行环境身份、原始文件哈希和具体耗时。完整世界及有序事件与相应原始两步窗口一致；这项检查不替代完整业务覆盖和性能测量。

`prepare_bed_destination_probe.py prepare --baseline <基线提交> --output <新overlay目录> --input <完整R1终态.bin> --reference <原R1目录>`只生成两份床查询源的A/B及独立counted版本，不复制完整工程、不运行引擎。B仅移植声明的床查询函数，其他在研改动排除；完整函数逆变换与counter移除均核对原字节。`install --overlay <overlay> --project <基线冻结工程> --variant a/b/a_counted/b_counted --record <新安装记录.json>`先校验基线全部game与docs/data Git对象、原生库及完整输入，再安装对应源；其他业务源存在差异时拒绝。

`bed_destination_probe.gd --input=<完整终态.bin> --output=<新结果.json> --mode=plain/counted --iterations=1000`从保留全部角色、设施、预约、身份和随机流的事实中，只读取合法地面角色及已发行原Move。非地面和待发行Move单独列出，不将其改造成合法查询。普通goal、原局部路径停点及当前完整身体查询分别记录，全事实Oracle、完整世界只读校验和结果哈希在计时外执行；plain三个独立进程对分别比较，counted进程只记录实际view和goal-region次数，不提供耗时。此局部查询结果不替代完整160人模拟步或业务覆盖。

[床停点局部验证](../../../docs/reports/2026-11-12-bed-destination-query-performance.md)记录选例结果、三对纯查询耗时、独立计数及原始归档，分别标明完整终态的实际人数、合法查询分布和未测范围。

`prepare_movement_contacts_probe.py` 与 `movement_contacts_probe.gd` 比较接触查询的单侧排序候选复用。完整输入、可逆A/B来源、普通／首接触两种模式、全部原Move及local corners、独立全事实oracle、分离计数和三对查询流程见[专项说明](../../../tests/acceptance/movement_contacts_candidates.md)。原始完整终态没有本步已接受扫掠，不为性能输入伪造该事实；两侧非空与历史扫掠由功能边界覆盖。该工具只测接触子查询，不能作为160人整步验收。

`prepare_clinical_diagnostic.py prepare --base-project <冻结工程> --output <新诊断工程> --input <原输入> --reference <完整plain轮次目录>` 构造可逆的临床计时诊断。原代码的逐 tick 探视扣减和终结清零分别记录，首个观察器错误保留步前、步后及实际分支当刻的家属、病房、患者、身体、移动、医疗和让位事实；独立几何只读取实际房间格与完整身体，不调用业务报价或移动。移除注入后原文件及方法体逐字节还原。诊断继续使用 `--profile-stages`、原 1000＋6000 窗口及业务覆盖门槛；即使覆盖断言失败，也须执行 `verify --project <诊断工程> --diagnostic-output <诊断轮次目录> --reference <plain轮次目录>`，独立核对完整世界和有序事件二进制哈希、阶段记录、源码、输入、引擎与原生库。带 hook 的整步耗时及阶段占比只用于归因，不能作为优化收益或性能达标证据。

同一业务实现的 plain 与诊断运行可用 `--outcome-reference <plain目录>` 核对完整终态和有序事件编码哈希，旧参数 `--exact-reference` 兼容。该参数是业务输出见证，与已经退役的临床容量 reference 算法无关，不要求新规则与旧内核逐帧一致。`paired160.py` 默认只记录两个版本的完整输出，只有明确要求全部输出相同时才用 `--require-outcome-equality`；仍须分别满足需求定义的业务结果。

来源清单、源码/输入/引擎/DLL 哈希、线程与进程条件、每步原始时间、工作增量、命令、完整世界校验及业务结果都独立保存。无窗口模拟步结果不证明实机帧率、GPU、完整 Release 矩阵或两小时稳定性；本场景也不覆盖 UI、存档生命周期、整医院日/季度和全部临床方案。
