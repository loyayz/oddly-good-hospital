# 160 人混合临床与运营场景

`mixed160-clinical-ops-v1` 是独立的性能矩阵行。原 `comprehensive160-clinical-family-v3`、完整输入 `752924c562f275804cee40cbd2a8760f8f0780cab3276a04330db63a2866e780` 及其全部压力请求继续保留。

两行的当前业务负载不同。混合行将原行 84 份尚待 GP 的输入改为 10 份待一次检查、6 份待原医生复核和 68 份待常规治疗；这 84 份原 GP 请求仍在原 v3 输入中验证。不能将混合行更快、拥堵减少或覆盖增多解释成程序优化收益。每行单独冻结输入、建立基线，并只在本行相同完整输入上比较实现。

## 准备边界与账目

`mixed_prepare.gd` 复用原准备器的建造、真实员工开院和完整身体部署。默认 v3 入口仍调用原病例声明、原追加八人逻辑，并保留原名称及默认行为。

新增历史在任何患者票发行和患者首步之前声明。每人记录本次 Visit、原医生、原 FUR02、诊断状态、唯一既往检查（仅待复核组）、费用和合法方案依据；所有病症、身体绑定和临床原规则保持。历史来自统一规格 §§14–18 允许的操作前输入，不生成过去的 `service_completed` 事件，不声称执行过历史 GP、历史检查或历史抽签。

84 份新增历史包含 84 次 GP 与其中 6 次已完成检查，增加 174 份诊断收据。连同原 24 份历史，共 108 次历史 GP、8 次历史检查、224 份收据。全部逐人按当前内容价格通过 `HospitalLedger.post` 记一次；现金增加原价之和，不改开局余额来抵消。原账目保持。准备清单保存入队前后现金、实际新增账目、随机状态及逐人声明，核对收据与现金守恒。

临床人数同时列出原 120 人、追加历史患者 8 人、追加全新患者 0 人、追加合计 8 人和总患者 128 人。默认 v3 仍保留原追加全新 8 人的字段与内容。

历史声明不调用或重置随机流。员工开院仍执行原真实生产步；后续 GP、检查模式、治疗结果、家属资格及到院按生产流继续。两行不同的后续随机消费属于不同业务输入，不强行对齐。没有初始 WardStay、入床时刻、床绑定、Attempt、Session、未来恢复、家属请求或家属 Actor；住院和两类家属必须在真实前缀或采样内形成。初始零家属不提供家属覆盖。

准备完成后不推进患者步。前缀与采样继续保留全部合法到院、退出、家属、维修上门和其他自然请求，不以替换患者、取消工作或维持人数改变实际负载。

## 命令与验证

使用同一次隔离工程准备和导入，分别生成默认 v3 与混合输入。已有输入、清单或失败边界的输出目录均拒绝覆盖。

```powershell
& <Godot控制台程序> --headless --path <隔离工程> --script res://tools/performance/current/comprehensive_prepare.gd -- --output-dir=res://.cache/<新v3目录>
& <Godot控制台程序> --headless --path <隔离工程> --script res://tools/performance/current/mixed_prepare.gd -- --output-dir=res://.cache/<新mixed目录>
& <Godot控制台程序> --headless --path <隔离工程> --script res://tools/performance/current/mixed_input_contract_test.gd -- --input=<新mixed目录/mixed160.input.bin> --v3-reference=<只读原7529输入> --v3-generated=<新v3目录/comprehensive160.input.bin> --output=<新契约结果.json>
```

契约检查不推进模拟。默认 v3 的完整 typed facts、RNG、身份、账目、初始病例及真实准备步数须与原 7529 输入一致；二进制元数据差异逐字段记录，不能忽略业务字段。混合输入仅允许批准的 84 份 Visit 历史和对应票种、174 份账目及其 revision 变化，以及原所有者同步的 84 个体验阶段投影和最终开放入院命令的 revision。投影按批准病例范围独立推导，相关集合的其他字段仍全量比对；尤其身体、位置、设施、员工、班表、库存、磨损、研究和随机状态必须保持。历史收据的金额、原医生、检查次数与方案从内容和病例合同独立核对。

```powershell
python -X utf8 -B tools/performance/current/campaign160.py --engine <Godot控制台程序> --input <mixed160.input.bin> --output <新smoke目录> --scenario mixed160-clinical-ops-v1 --smoke
python -X utf8 -B tools/performance/current/campaign160.py --engine <Godot控制台程序> --input <mixed160.input.bin> --output <新资格目录> --scenario mixed160-clinical-ops-v1 --repeat-number 1 --require-coverage
```

`--scenario` 是可选预期标签，缺省时保留原 generic 入口，不额外限制没有场景标签的普通合法输入。正式 v3 行显式指定 `--scenario comprehensive160-clinical-family-v3`，混合行显式指定 `--scenario mixed160-clinical-ops-v1`；标签不符时在实际模拟前拒绝。`paired160.py` 可选透传同一参数，默认不传。未知场景使用 `--require-coverage` 时仍按原规则拒绝。`scenario_cli_contract_test.py` 仅检查原默认 argv、显式标签、成对透传及原窗口/线程/覆盖选项，不启动引擎。

两行使用同一原观察器和同一运营命令，全部覆盖计算与门槛不变。每步 0.1 秒，1000 个真实前缀步加 6000 个采样步，app 主线程、四个环境任务、`OMP_NUM_THREADS=1`。每轮要求 P95 ≤ 10 ms、P99 ≤ 15 ms、普通步最大值 ≤ 30 ms、速度比 ≥ 0.99，并单独检验实际人数 ≥ 144 的连续至少 1000 样本。

初诊、检查、复核、普通治疗、手术、苏醒、护理与返房仍须有采样内真实工作和相应完成事件。研究、培训、清洁、装修、维修与升级保留实际工作增量；工单完成单独记录，命令接受或对象存在不代表工作。采购须有新付款和库存收据，耗材须由实际 Attempt 领用。

陪同入房与有效探视沿原门槛；另检查每人的 300 有效 tick 是否完整累计、是否真实离院，以及陪同生活后先回房、手术室外等待实际发生的范围。历史、前缀或患者终结清零不能补采样计数。没有发生的完整家属闭环继续标为未覆盖。

单梯动态拥堵、家属合法概率未命中、短服务全部在前缀完成或密集区间不足，都可能使这一输入资格失败。失败保留证据，不自动重抽种子、延长停留、减少病例、修改工时、增加资格或降低门槛。两步 smoke 只验证入口；输入契约通过不等于功能覆盖通过，更不代表性能达标。
