# Formal operation cards and observation boundaries

The visible Release runner and `operation_driver.gd` execute the original interfaces below. `after_real_seconds` serializes declared operations by real capture time; pending work is never skipped. An available dispatcher establishes an execution path, while each operation still requires its named legal input, actual result, displayed-frame evidence and applicable assertions. Missing prerequisites and results remain explicit acceptance backlog.

## Completed-step signal contract

The capture requires the generic `GameSession.tick_completed(result: TickResult)` signal. Both real completion paths in `GameSession.advance()` append their real result and emit once, immediately before `prepare_next_day()`. At that point `HospitalSimulation.step_nonblocking()` has completed all business stages, incremented the world tick, called `space.finish_boundary()` and cleared `_step_context`. The ordinary accumulator path has already debited the original 0.1-second tick; the resumed path already cleared its wait accumulator. Neither a null pending result nor a retried poll emits a completion.

The current TickResult exposes `started_engine_us` from the original context and `completed_engine_us` from the original finish read; `elapsed_us=completed_engine_us-started_engine_us`. `main_elapsed_us` accumulates every actual execution slice including null pending returns; `elapsed_us-main_elapsed_us` is between-slice wall time, not worker CPU usage. These observations do not enter facts or saves. The listener's first operation reads native `PlatformArrivalMath.monotonic_clock()` and records the real notification QPC separately. Original engine start/end are joined through QPC/engine/QPC brackets; the notification is later than the original finish and cannot substitute for it.

The signal must not call the kernel again, change a business field, consume randomness, submit a command, await, manipulate the active scene, retain a mutable world snapshot, or alter a TickResult. The formal listener only reads the result/current boundary and appends local serialized telemetry. The resumed branch can emit before `running_slow` is updated; listeners use the real result and do not reinterpret that prior display flag as an unfinished step. A signal is a read-only contract, not a language-enforced immutable payload. Untrusted/general listeners would need an explicit policy against reentrancy.

The dispatcher is once per actual completed step, with cost proportional to listeners; a no-listener emission still has a constant dispatch check. No numeric overhead is established by static inspection. The full presented frame includes listener, encoding and flush overhead. `TickResult.elapsed_us` was finalized before notification, so that kernel metric does not include the observer itself; the observer cost is never relabeled as zero full-frame work.

`formal_root.gd` constructs the original GameSession and connects it after composition. Its original switch method constructs the original new session; the observer connects that new session immediately after the original publication method returns, before a later `advance()` can run. It never constructs another session just to observe it, which would repeat `enable_preparation()`. Optional `playback_changed()` notifies after the original pause/resume/speed/watching state change, with early-return paths unchanged. The runner expects a no-argument playback signal; absence is a declared segmentation gap.

## A. Real maximum-room input to full feedback

1. The external Windows controller focuses the actual game and original building controls. It opens the original building panel, selects the original build-room mode, room type and door, and sets the legal floor/origin. It arms `preview_input_observer.gd` before the measured edit/drag. Programmatically changing SpinBox `.value`, calling `_request()` or `draw_room()` directly is a callback experiment, not this real-input latency case.
2. The helper's `_input()` first samples native QPC, then engine time, for each actual keyboard/mouse callback before normal GUI routing. The external controller logs its separate OS send QPC. Engine receipt, external send, complete result callback and actual displayed frame remain distinct endpoints. Real drag press, motion and release or original text commit continue through the original handlers.
3. Each input records the observed generation before dispatch and after dispatch. The original panel's `preview_changed` signal is connected after AppRoot's own overlay connection. Partial outline feedback is recorded separately. Superseded/cancelled queries remain in the operation timeline and do not become completed samples.
4. A terminal result requires the current original job's `complete`, not only `result.ready`: the current implementation sets `ready=false` on a completed failure. The helper checks result generation and session binding, records the original complete outcome/reason/units/atomic overruns, first/last input to that result and the whole operation's first input to target result. Repeated per-frame emissions are deduplicated by generation. If several inputs coalesce before the deferred observation, those observed bounds stay explicit; no missing per-request start time is reconstructed.
5. The result callback establishes current complete-result/overlay readiness, not final display. Preserve that marker and external input QPC brackets; correlate with an actually displayed frame after the marker, using any required pixel/screen corroboration that the final scene contains the result. A draw callback or engine-frame count cannot establish the displayed endpoint.

The accepted input domain permits up to 96x96/9216 cells, but an entire-floor room has no owned public cell outside it. Original room rules require at least one door to actual public space (`BuildService._public_door`, lines 711-731), and the 1F entry buffer must remain free (`BuildGeometry.occupied_error`, lines 161-163). Therefore a successful 96x96 whole-floor rectangle must not be invented. Separate the maximum-domain **complete failure** case from the largest prequalified **successful** room case. A 96x95 rectangle leaves one row in theory; this geometric bound alone does not establish legal doors, body fit, transit, evacuation, funds or a valid saved hospital. The complete real successful precondition must prove those rules before capture. Irregular larger legal shapes require the actual supported input path; do not inject a `cells` array directly and call it player input.

The dense Fixture already contains 64 rooms/1200 props, so a whole-floor preview there can fail early on real overlap. Record that failure, but do not count it as the successful full-check maximum-room sample. Use a separate legal operation-before-boundary hospital/floor when necessary. Sample counts and P95 are based on actual complete requests; a single successful sample, visible outline, or endlessly superseded sequence does not establish P95<=200ms.

The inspected implementation also has a structural sample-budget concern: BuildPanel calls `BuildPreview.update()` once per process frame with its default `maximum_units=128`, while the collect phase advances one cell per unit. Collecting a 9120-cell 96x95 candidate alone needs at least 72 updates, before the remaining checks. At a 60Hz capture target, that callback count is already incompatible with a 200ms cold complete-preview expectation. This is a static unit-count bound, not a measured presented latency; the final implementation and actual trace must resolve it without changing the legal input, hiding superseded time, or treating a warm cached query as the cold case.

Failure atomicity is checked on an already paused complete boundary with no queued commands: snapshot original facts/RNG before preview, perform the actual preview and compare facts/RNG afterwards; submit the original exact-quote command once where the case requires commit. For expected commit failure, use a legitimate stale quote or now-occupied legal target, retain the source/target owners and inspect the original receipt. Do not let free-running unrelated steps invalidate a whole-world before/after comparison. Expensive oracle/hash snapshots belong to a separately labeled correctness run or explicitly measured harness cost, not a hidden subtraction from the timed user operation.

## B. Resource cold/warm/reclamation operations

The original shared-scene cache has reference-counted release, not a public 'evict active visible object' method. A deliberate call to the **original** `HospitalView.bind()` is named `forced_current_view_rebuild`, rather than misrepresented as a narrow cache-entry eviction. Capture current camera transform/size and presentation selection/follow intent, call the original bind on the same actual world/floor/session, then restore only those presentation settings through their real view interfaces or corresponding camera properties. Preserve the new view generation produced by bind. Do not restore old resource tickets, model instances or binding generations.

The original bind retires nodes through `release_tree()`, releases the last visible scene users, clears batches and pending tickets, and requests current entities again. Keep originals in the retiring accounting until actually released. Rebuild, manifest hash checks, allocation/upload and late-ticket rejection occur normally and stay in the frame/memory sample. World facts, RNG, active movement, clinical reservations and elapsed work must not change because of viewing/reclamation; verify that on the separate paused correctness boundary. In the timed free-running case compare business commitments and original movement/work semantics, not identical whole-world hashes across elapsed ticks.

For navigation-cache stress, `_trim(0)` uses the owner's existing reclamation path and preserves its accounting/pruning contract. Do not clear `_entries`, `_sources`, movement dependency versions, active routes, request queues or reservations manually. After eviction let the next original movement/query execute and verify real arrival/safe handoff and unchanged clinical charge/resource ownership. This is a different operation from graphical resource reclamation and must have its own marker and measured responsibility.

There is no implemented button for forced eviction. The explicit harness invocation is an acceptance operation on derived caches, not a new product business branch; real UI viewing/camera/floor operations separately provide normal cold/warm behavior. If 'active graphics eviction' requires a narrower action than original bind provides, that evidence remains unavailable until a general cache-owner operation exists. Do not synthesize it by releasing resources still referenced by active nodes.

## C. Two hospitals and main-thread load phases

The formal profile must contain two different valid UUID hospitals, each with original committed snapshots. Fixture UUID depends on actor count: two same-count raw Fixture inputs may have the **same** UUID and do not establish two hospitals. Seed/import the second hospital through original `HospitalLibrary.create()` / import/create workflow before measured capture, wait for the original asynchronous receipt, and record source snapshot/content identities. Do not change `hospital_id` on a live raw fact dictionary merely to bypass this condition. Same-count second hospitals need an actual separately created/imported identity; different actual populations stay different measurement groups.

Start the switch via the original continue action. `_start_switch()` changes requested speed to zero, drains at its original command boundary, and begins a real source checkpoint. The original receipt drives target loading. Do not call `_prepare_switch_candidate()` directly to skip the source save, clear a pending source step, or set `_candidate` to avoid reading a real snapshot. Resolve outstanding drafts through the original cancel/confirmation UI; do not set `_draft_leave_confirmed` from the harness.

The new read-only wrappers observe these spans, preserving every original return/failure path:

- `snapshot_begin_world_main_inclusive`: validation, estimate/budget, original `world.freeze()` and thread launch, including deferred saves once actually entered. It is not isolated copy cost and cannot alone satisfy the 25ms copy metric.
- `snapshot_world_validate_main_inclusive`: original WorldState construction, validation and manifest/summary checks.
- `snapshot_read_decode_validate_main_inclusive`: original metadata/budget checks, chunk reads, actual decoder and validation.
- `continue_hospital_main_inclusive`: latest-commit search/recovery or exact requested commit through the original method.
- `prepare_switch_candidate_main_inclusive`: original load/migration, candidate validation, view binding, original old-session disposal, kernel/session construction and UI publication.
- `management_panels_bind_main`: all actual panel attach/rebuild work.

These scopes nest. Do not sum inclusive durations; any remainder must be explicitly named an unattributed measured main-thread remainder, not guessed separate asset/kernel costs. Only main-thread calls append to the main observer buffer; worker invocations are not relabeled as main-thread load. User switch start -> source checkpoint receipt -> target loader -> root publication -> first correct displayed target frame all have distinct endpoints. Preserve both user-visible switch total and actual target-load path; do not silently apply the load threshold to only a small nested decode span.

On success verify target hospital/session, loaded snapshot tick/RNG/receipts/commitments, actual current floor fallback, current binding generations and the original paused state. Resume only through a separate explicit original speed action included in the operation plan. Return to the first hospital via the same complete path; its inactive world must not have progressed.

The observer retains each successful original `_begin_world` source witness by its real `snapshot_id`. It checks hospital/tick/revision against the original freeze request, records RNG, and, when the scenario declares `required_session`, captures that named Session, Visit, attempts, supply issues, preparation, ward stays, tickets and directly referenced actors/resources. This is an explicitly scoped clinical witness, not a second whole-world checksum. The original canonical JSON encoder and loader still own whole-payload integrity. Witness copying/encoding cost is recorded and remains in observed frames.

`save.required_session` checks that the real named Session is still in progress before starting the original save. For a round trip to that exact mid-work or large-world save, `switch.snapshot_operation_id` resolves only the successful original save receipt's target `snapshot_id`; a missing or foreign receipt fails the operation. `verify_snapshot_witness=true` requires both the original loader's returned world and the published target world before resume to equal that source identity/RNG/clinical witness. Stability continues to use latest committed checkpoints on return, rather than resetting either hospital to a seed.

For failure, request an actual absent snapshot with a valid UUID through the same original action, or use a separately prepared invalid snapshot case. Never corrupt the only reference database during a timed run. Source checkpoint may legitimately be committed, but target publication must not occur: the original hospital/session/layout/clinical facts and draft rules remain valid, and it stays paused. Verify source content on a complete boundary and original error/receipt. Missing target evidence is a failed load case, not a successful fast load sample.

## D. Actual shift and day-preparation waits

Use a named complete snapshot generated by real original advancement before the boundary: original RNG, plan, staff schedules, current sessions, bed commitments, queue tickets and balances are preserved. No arbitrary assignment to `sim_tick`, remaining work, deadlines or plan emptiness is allowed. Preparing such an input may take the original time; once generated under unchanged owners/content/environment it can be reused read-only and independently cloned for each case.

The scheduler reads `shift_seconds`/`TICK_SECONDS`, `shifts_per_day`, and the original per-staff schedule; the observer records actual `last_schedule_slot`, `on_shift`, `block_new_work`, rest debt and reason on the completed step whose **executed** tick hit that boundary. The returned tick is already incremented, so deriving 'handoff happened' from only the returned tick's division would be off by one. At least one actual occupied service/ward and an available real relief path are required for the safe-handoff case; a second case legitimately lacking relief must pause and later recover through original attendance/movement, not a teleported nurse.

Arrivals `boundaries()` returns false while the sealed original day capacity is incomplete. `step_in_progress()` and original `_step_context` provide the pending-step observation; the same full TickResult eventually includes the real waiting span. `arrival_day_planned` occurs only after the actual solution is committed, and the original day RNG/opportunities are checked for one freeze, not resampled on each poll. The runner records pending observation bounds separately from original full-step elapsed; it never calls a background poll loop or a blocking replacement step. Initial warmup does not wait for future-day jobs to finish: 32 actual complete steps, observed actual work, ready visible resources and the original complete boundary establish the initial gate. A future background job remains ordinary capture load.

Pause/focus/save arriving during that wait does not truncate it into a new loading/prewarm segment. Keep the original started-step cost in its original segment until completion. Preparation remains ordinary operating load. Do not mark later boundary caches or blocked work as warmup just because they produce a long frame/step.

## E. Two-hour real stability schedule

The original requirement is two **real** continuous hours, original three-real-minute automatic saving, a room modification every 15 real minutes, and a hospital switch every 30 real minutes (`docs/design/06-validation.md:1041`). Set `minimum_capture_real_seconds=7200`; set the independent safety timeout to warmup + 7200 + genuine pending-operation/tail allowance, for example 10800 as a stop guard, never as a completion substitute. The small runner now rejects an early stop even when 1000 frame/step minima were already reached. No multiplier, simulated-time jump, shortened work or accelerated autosave interval is permitted.

The scheduler emits scheduled and actual start/end times using monotonic real time. It keeps one original command in flight per scenario operation, preserves stable command IDs and observes real receipts. A due operation waits for a safe original boundary and prior work; it is not discarded or declared complete when a prior operation runs late. Coincident 15/30-minute events are serialized and their actual delay retained. At least 7200 seconds plus all due operations and the final real displayed tail must finish before scenario completion; stopping exactly at 7200 while the final modification/switch is pending is incomplete.

| Real elapsed schedule | Original operation | Required completion evidence |
| --- | --- | --- |
| Every original 180-second autosave deadline | AppRoot's existing autosave and pending-auto flow | Original slot kind `auto`, actual request/receipt identities and duration, copy/main span, failures and peak resource samples |
| 900, 1800, ..., 7200 seconds | Prepare a real room resize/move using a prequalified alternate target; wait original evacuation/safe handoff; explicitly refresh original quote and submit `remodel_apply` | Prepare/apply accepted receipts, actual source/target geometry change, original order `state=applied`, retained unaffected equipment/work promises, exactly one corresponding ledger post |
| 1800, 3600, 5400, 7200 seconds | Original switch to the other committed hospital, then explicit original resume action | Source checkpoint, target decode/validation/publication, new session signal connection, correct first displayed frame and paused-then-requested playback trace |
| Throughout and at end | Real clinical/maintenance/research/schedule/day processing | Progress/no deadlock, original RNG and command identities, actual charges/resources, no repeated settlement, actual resource/node/working-set trend and final convergence |

Room edits require a **real change**, not an empty command or resizing to the same geometry. Each hospital needs two alternate prequalified legal layouts/door arrangements or enough valid new targets for all its assigned edits. Choose an actual occupied room when safe-exit/handoff responsibility is part of the case. `remodel_prepare` creates the original `preparing` order; original `dispatch()` performs real evacuation and suspension. Wait for `_waiting()` to clear, obtain one current `preview()`, and explicitly submit its exact `price/refund/layout` quote with `remodel_apply`. If a quote becomes stale or an apply fails, preserve the preparing order and original source facts; record failure and require a new explicit current quote/confirmation. Do not set order state, move an actor, erase a preparation/ward stay, release a bed, or automatically pretend that a failed command succeeded.

For periodic readiness, query the original cheap waiting condition at a declared cadence, then call the complete original preview only when eligible or when the scenario explicitly requests fresh feedback. Include all actual query/preview cost in the timed run. Do not poll a deep full preview every frame just to implement the harness schedule.

Stability remains one continuous process with ordinary transitions preserved. Performance populations are split by actual hospital/session, visible load/density, window, UI/scene scale and playback state; the two-hour requirement does not authorize pooling unrelated hospital ticks, light and dense frames, or explicit load phases. Report observed peak cadence and process lifetime peak separately. A working-set increase above the original 10% stability criterion requires a bounded-cache explanation and actual eventual convergence evidence; a short return to the first hospital does not establish that convergence.

Completion must list actual autosaves, all eight due room changes, all four due switches (including recovery of the final one), elapsed real time and any remaining command/save/thread/pending step. The sequential dispatcher supports the real deadlines, original remodel path and original switch path. The full stability configuration still needs eight prequalified real alternate layouts and four real target snapshots; the default camera/save operations do not fulfill that contract. A 7200-second minimum alone is insufficient.

## F. Operation configuration

Every operation has a unique `id`, `action`, optional `after_real_seconds` and `timeout_real_seconds`. Source hospital/session identity is retained throughout asynchronous work. The existing camera/panel/floor/save actions keep their original fields. Additional actions use the following fields:

| action | Fields | Actual completion and retained gaps |
| --- | --- | --- |
| `view_rebind` | None | Original same-world/floor/session bind, original release_tree, new generation, zero pending bindings and retired nodes; restored camera/selection are presentation state. First correct displayed frame and complete resource residency remain external |
| `navigation_evict` | `minimum_followup_steps` default 1 | Original `_trim(0)` settles its own allowance/entry accounting, followed by real session steps. Specific real arrival/charge/resource assertions belong to the scenario; allowance bytes are not allocation bytes |
| `wait_autosave` | `include_previous_in_capture` default true | A real original `slot_kind=auto` receipt in this capture; failures remain failures. `autosave_deadline/save_request/save_receipt` preserve due, start and receipt markers |
| `seed_hospital` | `input_path` absolute original input binary | Independent validation/content identity and distinct original UUID, then original Library.create and actual checkpoint receipt. No live ID rewrite |
| `switch` | `hospital_id`, optional `snapshot_id` or `snapshot_operation_id`, `verify_snapshot_witness`, `expect_failure`, `resume_speed` | Original continue action, source checkpoint, original load/publication, new original session and ready target bindings. Named-save return resolves the actual successful receipt and verifies its source witness when required. Successful load must be originally paused; resume is explicit. Expected failed load must retain source session and pause. Final displayed target still requires external correlation |

The preview driver publishes `input-request.json {id,status:armed,pid,hospital_session,fields:[{name,client_point:[x,y],text}],expected_draft}`. The actual LineEdit local center is transformed by `get_viewport_transform() * get_global_transform()` into physical client pixels, including root content stretch. `get_screen_transform()` omits that stretch when the root embeds subwindows. The external driver validates the owned foreground PID and physical client bounds in a DPI-aware scope, converts the point through Windows `ClientToScreen`, sends real Windows input, and atomically writes `input-ack.json {id,ok,error,send_begin_qpc,send_end_qpc,qpc_frequency,pid,actual_fields}` with both client and actual screen coordinates. A false ACK fails the operation. Engine Input.parse_input_event, direct SpinBox changes and direct preview requests are never substitutes for the measured real edit. The helper waits for actual target draft/outcome and original terminal result, including completed failures whose `ready` is false.

The remaining executable-scenario backlog is the prequalified largest successful room input, real alternate remodel layouts for the eight periodic edits, the corresponding clinically occupied/relief and genuine preparation-wait cases, and independent full resource allocation/residency evidence. The operation driver does not generate fake entities, shorten legal work, teleport participants or turn missing prerequisites into success.
