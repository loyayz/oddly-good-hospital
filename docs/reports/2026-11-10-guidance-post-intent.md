# 导诊队首真实到岗与 160 人性能验证

## 实际原因与修复

保留的 `4a79a6b` 三次测量中，完整步均值 72.240ms，移动根区间平均 47.660ms、临床调度 6.896ms、候诊调度 4.525ms、环境采样 4.268ms、导诊调度 0.514ms。导诊的主要推进障碍不是自身调度区间耗尽 CPU，而是实际走到服务位的交接。分段是经过时间区间，尚未逐个计量移动辅助函数的自身 CPU 耗时。

已复现的三处真实导诊队首，其静态几何报价通过，完整报价明确被附近来人的身体阻挡。队首仍在排队点，实际服务位还要挪约半格；旧 `_approach_desk` 却要求整个操作区域已空出、并取得使用预约，才发布这段移动。过路者面对没有移动订单的队首只能绕开或等待，队首因过路者占着操作区而不能发起移动。先前“目标原地等待”实验进一步锁住了这些身体，导诊回执降至 6，已经撤回；负面证据完整保留。

合法窄口用例独立复现：护士已真实到岗，队首已入队，过路者有原目的地，两名固定人物保持。几何可行、完整报价因过路者失败，旧流程 300 步未完成。修复后正常与当前生产保存冷恢复均用 76 步完成，包含完整 60 步导诊，过路者到原目的地；五人的真实身体、扫掠、速度预算和世界校验通过。

修复沿原调用链拆开意图与使用：`_approach_desk` 用现有几何报价选择真实服务位，发布 `to_counter` 意图；`_gather_counter` 让双方按原普通移动真实到位，随后仍以 `reserve_facility` 执行完整动态核验，成功才进入 `working`。原台、护士、队序、票、六秒工时及开工冻结工作率保持，没有提前安排临床目标或取得医疗资源，没有通行优先权、让行承诺或整层动态搜索。

存档允许尚无预约的行走意图；实际工作必须持有与病例和护士一致的预约，未取得预约的伪造工作状态仍拒绝。同台唯一活动队首保持，原有实体及预约权限继续约束每个真实移动步。原队尾目标到达后才重新判断的规则没有修改。

## 功能与测量范围

新增正常/完整冷恢复用例及原 15 个 GUIDE 到场、跨层、阶段接续、护士暂停/交接、离场、队序、建台/拆台、移动所有权、保存与动态入队重试用例通过。CLIN-24、25、27、37 选定交接通过，CLIN-37 含目标被占与恢复的十个模式；WIDE/LOST 正常及完整冷恢复、受阻局部动作 44/43 步通过。完整临床 LIVE/RESTORE 均最终 tick 6376，真实执行全部手术、苏醒、恢复、护理、查房并离院。

最初一次诊断前提使用错误桌体位置且字典实体键类型不符，未形成合法业务复现；日志保留，不能算业务失败。修正后的合法前提与失败/通过、源码、执行命令见功能证据。所选范围通过不代表全量验收或全场所有人物到达；固定初始 160 人测量结果如下。

从已撤回实验的严重拥堵终态继续 400 个真实全模拟步，未减人或改派原任务：三个原队首都获得了 `to_counter` 移动意图，两个实际到达服务位，但一个仍被其他来人的身体挡住操作区，另一个随后因生活需求离队；三个在此窗口均未完成导诊。因此本修复证明了原交接环节的缺陷与合法窄口的真实恢复，没有证明该历史拥堵快照已经全部恢复。原始固定输入的三次测量用于另行检查新流程的整体表现。

功能、合法/非法前提、严重拥堵跟踪及源码身份见 [证据清单](evidence/2026-11-10-guidance-post-intent/manifest.json)。

当前版本还包含上游 `97bbfe5` 的环境无来源观察直接完成路径。各主体观察与消费规则保持，但实际 worker 数可小于四；测量必须分别记录主线程直接观察和真实 worker 任务，不能沿用旧版每步四个任务的假设。模拟步、初始化、Windows 选核和画面范围分别说明，暂不验证画面。

采样期每步末活动移动订单为 96～125，平均 117.5485 个，订单数不等于该步成功位移人数。移动阶段既有必要的当步身体安全核验，也有受阻时产生的额外路径工作。第 1 次 tick 2637 完整步 378.827ms，其中移动区间 342.068ms；该尾部样本明确落在移动阶段。

代码还表明，`_local_resume` 在真实达到局部拐点后尝试回接，实际接触经 `_local_collision` 才推进被尝试的原路线目标；原路线游标在真实回接后才前进。`_local_return_around_nearby` 从实际位置及意图终点附近的设施/身体索引取障碍，按横纵坐标构造短连接。坐标数为 nx、ny 时，预建连接数量为 `nx + ny + 2*nx*ny`，之后逐条检查静态扫掠、床岗位和附近固定身体，取首个成立连接。重复构造及候选乘积是明确存在的计算来源，但尚无子函数计时证明它占移动 40.242ms 中的具体份额；不能将整个移动区间全部归给寻路或回接。

已验证的推进缺陷是：只有局部意图、实际下一步却受阻的人，曾使另一人无限等待；导诊队首尚在排队点时，又被完整操作区预检查阻止发布到岗意图。前者按对方真实下一步是否可离开判断，后者将几何意图与实际使用预约分开，均有修改前反例、真实最终到达及当前生产保存恢复证据。完整动态预约仍在真实到岗后执行，移动每步仍核验身体安全，未增加固定优先权、让行承诺或运行时整层搜索。

下一阶段的简洁方向是先独立计量普通实际步、路线调度、真实碰撞和回接候选的次数及耗时，再验证是否值得保持原顺序按需生成连接，避免在首个可用连接之前预建全部数组；静态几何可按既有楼层/身体身份缓存，动态身体和预约仍按真实步核验。候诊及临床的重复候选/准备也应先分清触发次数与有效结果，再考虑复用。这些是待验证方向，当前版本没有加入额外缓存、候选截断、扫描降频或新交通规则。

## Windows 选核、多核与画面范围

六次都以 `app` 策略调用与应用入口相同的主线程原生函数：`applied=true`、`performance_cores`、`hybrid=true`、group 0、mask `fc03`、error 0，调用线程为 Godot 主线程 1。原生实现核验主线程身份并检查 `SetThreadAffinityMask` 成功返回，设置针对调用主线程，worker 继续由 Windows 调度。该记录证明测量入口设置成功；没有采集逐时刻落核分布，也没有默认调度三次对照，不能声称选核收益。

每个进程前缀加采样共有 3000 批、368460 个环境请求，processed = consumed = 368460，failed = 0。366291 个无来源观察在主线程直接完成，占 99.411%；其余 2169 个观察进入任务路径，共 2155 个任务，其中 820 个单任务内联、1335 个进入线程池，多个实际后台线程完成任务。完整结果仍按原请求顺序消费；覆盖键查询 2169 次，原生实际计算 78 次，fallback 为零。没有通过漏掉请求来减少工作，但请求总数会随合法业务演进变化；这些计数不能与不同版本的请求数强求相等。

配置四任务代表单批最多四个任务，不代表每步四任务或固定四核满载。当前测量未做 0/1/4 任务的同版本对照，不能给出并行加速倍率，也不能从环境区间下降推导整个游戏的多核收益。

本轮只测无画面的完整模拟步，含内部等待；实际 `GameSession`、呈现帧率、GPU、主线程实际调度轨迹和画面均未验证。没有新增引擎构建、原生代码变更或全量验收；功能结论限于前述选定交接。平均步耗时低于 100ms，P99 仍高于 100ms，尾部计算仍需定位，不能用这些数值换算实际游戏 FPS。
