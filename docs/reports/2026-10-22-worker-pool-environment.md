# WorkerThreadPool 环境采样受控试验

`WorkerThreadPool.add_group_task()` 已在完整160人窗口中执行，并**采纳为默认4任务路径**。最终生产复测公共平均下降3.08%、运营下降3.36%，GP平均退化0.96%、P99退化8.08%；之前两组公共下降6.56%、5.47%，GP下降2.37%、3.99%。部门阶段的直接诊断净收益约0.77ms/步，幅度小但保留采纳；串行回退、运营及GP退化、额外CPU成本全部保留。主要P99仍在候诊和临床，未声称各窗口稳定改善或正式验收通过。

原生产对照为 `a0d893b3ca57cb7e078fbf23b09a910846d43820`，其生产代码与 `d5f048e` 相同。生产集成将同一分片helper移入 `game/operations`，部门默认启用，保留原环境/空间注入及缺结果回退。复验工具只给工程副本生成控制runner。另修正GROW-72中已由原生产实现复现的过时采样次数断言，业务规则和性能阈值不变。10月22日的受控试验与10月23日的生产集成验证分别记录。

## 独立计算边界

部门采样先取得原有顺序的全部有效人物请求，按连续分片分配最多4个job。每个job拥有独立的 `HospitalEnvironment`、`HospitalSpace`、查询与缓存容器；主线程先准备当前设施、噪声、污渍和楼层格边，工作线程只借用只读来源、已冻结内容定义及覆盖结果叶子。

主线程使用 `add_group_task(_run_job,count,count,false,...)` 派发，调用 `wait_for_group_task_completion()` 完成清理和屏障。全部结果通过完整性检查后，才按原visit顺序消费；缺槽或坏结果整批回退原串行路径，发生在经验、怒气写入之前。实际job记录了非主线程ID，末批能看到4个不同工作线程；job数量不等于整个窗口固定使用4个线程。API和共享状态边界依据[Godot 4.7 WorkerThreadPool](https://docs.godotengine.org/en/4.7/classes/class_workerthreadpool.html)及[线程安全说明](https://docs.godotengine.org/en/4.7/tutorials/performance/thread_safe_apis.html)。

保留以下顺序与所有权：

- 水源的本人资格、当前展开、占用和真实路线查询仍在主线程，由原 `_water_usable` 按原候选顺序检查。工作线程只返回候选和已减噪声、尚未clamp的整数值；主线程补一次饮水分再执行原clamp。域外早返回不套用该数值完成过程。
- 每个人物的覆盖项在原处理位置合入主查询，随后执行原经验、原因时钟、怒气与详情结算，保留夹入的水源及候诊环境查询顺序。
- `active_operation_ids()` 会写世界运行时索引。来源准备在主线程完成，worker不会进入该lazy分支；不共享可写coverage容器、AStar或主空间服务缓存。
- 原8楼层、每层128个保留origin的规则不变。job临时映射在屏障后释放；分片间重复计算真实计数，不减少查询输入。自定义环境、null环境沿原串行路径；生产集成还保留自定义空间的串行路径。

初始化、来源准备、容器复制、派发、等待、校验、合并和串行结算都在原 `HospitalSimulation.step()` 计时内。没有步外预热或缓存恢复。每步附加job记录仅在诊断选项启用后、计时结束时读取，不混入plain对照。

仍为120患者、32员工、8访客，4层、64房间、1336设施；沿用同一公共360步、GP80步、运营40步输入与0.1秒步长。Godot 4.7.2 Windows headless debug及原生DLL不变；未改人数、阈值、轮询、请求预算、随机流或业务规则。

顺序为A1、B1、B2、A2，每轮均执行三个完整窗口。A是原生产代码，B是4任务试验，不含root或内部函数计时。各分位来自各自完整窗口，包含冷首步。

## 并行开销为何抵消大部分阶段收益

下表为root加轻量Worker计时的诊断，不与plain窗口拼接计算收益。公共使用最终helper，GP使用首轮helper；随后仅加强屏障后的缺槽/字段检查，其身份和全部旧结果均保留。

| --- | ---: | ---: |
| 原生产root部门采样 | 7.913ms | 6.451ms |
| Worker root部门采样 | 7.146ms | 6.035ms |
| 请求收集 | 0.373ms | 0.350ms |
| job懒初始化摊销 | 0.002ms | 0.004ms |
| 来源与私有缓存准备 | 1.106ms | 1.226ms |

| 其中水源许可与最终clamp | 0.482ms | 0.116ms |
| 各job经过时间之和 | 10.267ms | 8.128ms |

job区间重叠，最后一行不是线程CPU，也不能与等待相加。主线程应用已经包含水源和合并，不重复求和。其余部门工作和调用边界仍在root中。

公共部门只净省约0.767ms，GP约0.416ms；7.9ms阶段并没有整体变成四分之一。来源与私有容器准备、等待、收取以及顺序依赖仍需支付，worker经过时间之和也高于可直接节省的串行预算。其他未改动root阶段同样发生变化，因此完整步两组差值不是这些局部数值的严格因果分解。

运营root部门在原控制为8.232ms，首次Worker诊断8.816ms，后续带逐步记录的诊断7.491ms。首次诊断中1166～1169等步的采样和多个其他阶段同时变慢；后续诊断没有重现相同退化。逐步job记录完整保留，现有证据不能把首组退化精确归给线程等待、某个函数或外部调度因素。

首次功能批次中STAFF-32、OPS-11、OPS-18通过，另外两项失败：

- 新增检查以未建成医院作为患者准入前提，准入失败后索引空列表。改用原有合法已建成医院前提，准入失败显式返回原因；水源预期和判断规则不改。
- 原GROW-72要求 `sample_calls==1`，但测试先显式采样一次，随后弃候环境评分又采样一次；加上单独 `environment_at`，总观察3次、采样2次。临时恢复原生产game和原测试后实际复现该失败，原GROW-75同时通过。断言修为精确2次并输出该计数，没有放宽性能阈值。

修复后只重跑GROW-72/75，两项通过；另外三项复用首次通过证据。共5项选例通过，不表示专题或全量通过。新增检查实际覆盖0/1/4请求、嵌套查询与缓存顺序、完整经验/怒气/详情/员工日记录与随机流、custom串行、缺槽整批回退，以及饮水来源、当前身体、故障、真实预约和许可变化。4组未clamp整数边界单独标为数值函数输入，不宣称它们由合法医院流程产生。有限helper未覆盖跨层和域外Worker专项请求；正式全容量、内存及长期稳定性也未验证。

初次helper、失败功能结果、原实现复现和修复后结果均保留。复制检查前提的3次工具校验失败分别涉及已有测试目录、缓存UID与Windows换行，均未启动引擎。试验阶段生成的6份目标已与实测/功能副本逐字节比对；生产收口后的工具仅生成控制runner，也已核对与实际测量字节一致，并拒绝原仓库与已安装副本。

## 采纳与未完成项

[生产helper](../../game/operations/environment_sample_batch.gd)保留同一分片算法，部门默认启用4任务；可关闭并行作串行控制，自定义环境/空间与缺结果沿原回退。[复验工具](../../tools/performance/experiments/README.md)提供串行/1任务/4任务及诊断入口。候诊、临床预约和实际移动需要看到前面人物的提交，现有证据不支持把这些整个阶段直接放入group task。后续并行方向需要先找到其中真实可独立计算的只读批次，并计入快照、私有缓存和顺序复核成本。

各轮公共平均收益和前两轮GP平均改善作为短窗观测保留；最终GP退化、运营早期退化、CPU增加、控制组波动和未解决的主导尾步同时保留。不采纳“并行已使整步或P99达标”的结论。P95≤10ms、P99≤15ms、普通最大≤30ms保持；本次为快速debug诊断，未执行正式Release、完整容量、渲染、内存或两小时验收，正式性能验收仍未通过。
