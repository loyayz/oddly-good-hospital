# 第三阶段：内核Release性能检测

第二阶段性能检测未执行。第三阶段本次测量范围为160人、1×/3×正式内核，采集有效性与性能达标分别判定；本次性能结果：**未达标**。

历史160人两组实际推进速度均达到99%目标，完整步P95均超过采集时的4ms预算。当前采用下述重新推导的10/15/30ms预算，旧记录仍未达标。评审修复与优化后按160→320→640人逐档正式复测，每档1×/3×全部通过才进入下一档；失败后每档最多三轮优化、提交与复测，三轮仍未达标则停止后续档并记录原因。历史320人组已中止，没有有效正式摘要；640人组未启动，均不参与本报告统计或成本校准。

## 完整步与预算口径

一次完整步指正式`Simulation.step`执行当前已接入的命令、临床派发、移动、工作、需求积分、结算及快照边界，推进0.1模拟秒。尚未接入的到访、环境和互动等业务保留阶段位置，不能据此宣称完整游戏成本已测。现实CPU耗时与推进的模拟时间分别记录。

采集时4ms来自当时的数值配置和技术规格，属于历史项目预算。它不是社区同类游戏的统一标准，现有设计没有提供同类游戏耗时分布来证明该阈值。1×每秒执行10步，3×每秒执行30步，推进周期分别为100ms、约33.3ms；这些是维持模拟速度的周期，不能作为推荐单步耗时或画面流畅度标准。

当前[数值配置](../data/balance.json)和[技术规格](04-technical.md)采用`sim-frame-budget-v2`：模拟占主线程帧目标60%，其余工作预留40%，向下取整得到P95≤10ms、P99≤15ms、普通最大≤30ms。按新标准另行评估，1×的P95仍超标；两组P99达标，但最大98.5/66ms都超过30ms，因此两组仍未通过。原始摘要、4ms阈值及退出码不改写。

60FPS的整帧周期约16.7ms，还需容纳界面、场景投影和渲染等工作。模拟与绘制可以采用不同频率；[Factorio开发者的更新/绘制说明](https://www.factorio.com/blog/post/fff-70)也区分FPS、UPS及短时耗时尖峰。本次结论为“超过项目4ms预算，实际模拟速度达到目标”，画面流畅度仍未验证。

## 实测条件

原始证据目录：`.cache/validation/stage03/formal-v3`。构建与源文件哈希、设备、电源和后台进程记录保存在同目录。每组独立预热60现实秒、采样600现实秒；步耗时采用单调时钟和最近秩分位。

夹具保持160名实际在院身体，使用四份96×96合法移动楼层和原手术布局，保留10000层稀疏结构。额外居民沿真实路线持续移动，一个D23病例执行原接待、诊断、手术、护理和结算流程；患者实际离院后的下一边界补入一名移动居民。单个病例完成后不持续生成新病例，本次结果不能代表多站点临床满载。逻辑记录数与实际在院数分别记录。

完整step计时包含全部已接入阶段。额外居民的批量路径请求由夹具在步前准备并单独计时；临床派发与实际移动在正式step中。原始日志和OS观察仍计入实际推进速度；计时探针有独立开销样本，日志序列化和写入开销尚未独立量化。无窗口采集没有呈现帧或GPU指标。

## 运行与收尾

第二阶段提供基准准备、72组显示计划、原始记录、OS资源采集、报表和成本接入清单；性能检测跳过。第三阶段提供类型化世界/命令/结果/事实事件、稳定十阶段、会话播放控制、命令原子失败、账目幂等、独立回放及规则运行器。

空间优化以完整身体包络建立分桶索引，同步真实移动、承托、乘梯和离院；同一tick的规范化事实和十二条随机流比较另见等价证据。采集工具拒绝有Godot运行错误的记录。早期诊断中的Array类型互操作错误已修复，该批诊断保留为无效证据，不参与成本校准。

评审后的修复验证通过30项规则检查，包括负余额与未结算收入、命令幂等与原子失败、暂停/恢复，以及两类临床流程在不同速度与帧间隔下的完整事实一致性。回放入口补查发现读取预算回调返回类型不符并已修复：合法移动回放实际返回0，缺失确认位置、超范围坐标和畸形位置分别返回2且不产生输出。第一阶段历史报告中的保存、安装及绘制证据不被视为本次重验。

第一轮优化定位到tick2630的真实临床寻路：诊断完整步约68ms，其中同层寻路约62ms。一次同步寻路内预先整理地块、阻挡、门、实际设备占地和预约区域，保留原BFS顺序及身体检查。160人原算法与优化算法在tick80、2630、2700的规范化完整事实及十二条随机流一致；正式性能结果以优化后的600秒采集为准。
